**האירוע:** 23.10.26 · 11:00-16:30 · מוסללה רופטופ (Muslala Rooftop) · KIMIDA • HUNA • SURPRISE GUEST • GUYJI

## מסכים

| נתיב | מי נכנס | מה יש שם |
|------|---------|----------|

## הקמה

### 1. Supabase

1. צרו פרויקט חדש ב-[supabase.com](https://supabase.com).
2. פתחו **SQL Editor** והריצו את כל התוכן של [`supabase/schema.sql`](supabase/schema.sql).
   הסקריפט יוצר את הטבלאות, את פונקציות ה-RPC, את מדיניות ה-RLS ואת נתוני הזרע (3 סבבי מחיר + קונפיגורציה).
   הוא אידמפוטנטי, ובהרצה חוזרת על פרויקט קיים הוא גם מבצע שתי מיגרציות הרסניות:
   - **מסיר את כרטיס ה"זוגי"** (`price_pair`, `ticket_type = 'pair'`). הזמנה זוגית קיימת
     מומרת ליחיד ושורת המשתתף השנייה שלה נמחקת — `total_amount` המקורי נשמר, אז אם באמת
     היו הזמנות זוגיות כדאי לעבור עליהן ידנית אחרי ההרצה.
   - **מעדכן את שלושת הסבבים למחירים שבטבלה למטה**, כלומר דורס שינויי מחיר ידניים
     שביצעתם ב-Supabase.

   בנוסף הוא סוגר את הגישה הישירה של מפתח ה-anon לטבלאות `orders` ו-`tickets` (ראו "אבטחה" למטה).
   אחרי העדכון הזה צריך לפרוס גם את הקוד החדש, כי גרסה קודמת של האתר כבר לא תוכל לקרוא או לכתוב.
3. עדכנו את השורה ב-`events_config` לפי האירוע שלכם:

```sql
update public.events_config set
  event_name    = 'שם האירוע',
  sales_start_at = '2026-10-01 10:00+03',
  sales_end_at   = '2026-10-20 23:59+03',
  paybox_url     = 'https://payboxapp.page.link/...',
  helper_pin     = '<קוד סדרן, 6 ספרות ומעלה>',
  admin_pin      = '<קוד מנהל, 8 ספרות ומעלה>';
```

> **חובה להחליף את הקודים `1234` / `9999`** שמגיעים עם הסקריפט. בדיקת הקוד זמינה לכל מי שיש לו את כתובת
> האתר, ואין הגבלת ניסיונות — קוד של 4 ספרות אפשר לנחש בכמה דקות.

### 2. משתני סביבה

```bash
cp .env.example .env
```

ומלאו מתוך **Project Settings → API**:

```
VITE_SUPABASE_URL=https://xxxx.supabase.co
VITE_SUPABASE_ANON_KEY=eyJ...
```

### 3. הרצה

```bash
npm install
npm run dev      # http://localhost:5173
npm run build    # בנייה לפרודקשן לתיקיית dist/
npm run preview
```

> **פריסה:** הקובץ [`public/_redirects`](public/_redirects) (`/* /index.html 200`) מועתק ל-`dist/`
> ומטפל ב-rewrite של כל הנתיבים ל-`index.html` ב-Netlify וב-Cloudflare Pages, כך ש-`/door` ו-`/admin`
> לא מחזירים 404 ברענון. ב-Vercel הקובץ הזה לא נקרא, וצריך `vercel.json` עם rewrite מקביל.

## מחירים ולוגיקה

| סבב | קיבולת | כרטיס יחיד | כרטיס קבוצתי (4) |
|------|--------|------------|-------------------|
| מוקדמות | 40 | 80 ₪ | 280 ₪ (70 ₪ לאדם) |
| כרטיס רגיל | 80 | 90 ₪ | 320 ₪ (80 ₪ לאדם) |
| רגע אחרון | 40 | 100 ₪ | — לא נמכר |

יש שני סוגי כרטיס בלבד: `single` (1) ו-`quad` (4). הכרטיס הזוגי הוסר לחלוטין.

**סבב בלי כרטיס קבוצתי:** `tiers.price_quad` הוא `null` — וזה מה שמסמן "הסוג הזה לא נמכר בסבב".
ב-`/` הכרטיס הקבוצתי מוצג מנוטרל עם ההערה "כרטיסים קבוצתיים אזלו לסבב זה", ו-`createOrder`
דוחה ניסיון ליצור הזמנה כזו גם אם היא נשלחה בכל זאת.

הסבבים (`tiers`) מתמלאים לפי `sort_order`. הסבב הפעיל הוא הראשון שהקיבולת המצטברת שלו
עדיין לא נוצלה על ידי הכרטיסים שנמכרו (כל ההזמנות שאינן `cancelled`).

**כלל הקבוצה:** אם קונים כרטיס קבוצתי כשנותרו בסבב פחות מקומות מגודל הקבוצה — כל הכרטיסים
בהזמנה עדיין מקבלים את מחיר הסבב הפעיל. הספירה פשוט "גולשת" קדימה, והקונה הבא כבר מקבל
את הסבב הבא. הקיבולת הכוללת של האירוע, לעומת זאת, היא תקרה קשיחה: כרטיס קבוצתי שלא נכנס
בה נדחה עם "נותרו רק N כרטיסים".

**נעילה:** הסבב והמחיר נקבעים בבסיס הנתונים, בתוך `_create_order`. הפונקציה נועלת קודם את שורת
`events_config` (`FOR UPDATE`), ולכן יצירות הזמנה מתבצעות אחת אחרי השנייה: כל אחת סופרת, בוחרת
סבב וכותבת בלי שאף אחד אחר יכול להתערב. המחיר שמוצג בדף הוא תצוגה מקדימה בלבד. הסכום שנקבע
בפועל הוא זה שמופיע במסך האישור.

## זרימת התשלום

1. הלקוח שולח טופס → נוצרת `orders` בסטטוס `pending` + שורת `tickets` לכל משתתף.
2. מסך אישור מציג את הסכום ואת הכפתור לפייבוקס, עם ההנחיה לרשום שם מלא בהערת ההעברה.
3. המנהל רואה את ההזמנה ב-`/admin` תחת "ממתינים לאישור", ולוחץ **אשר תשלום**.
4. באותו רגע הכרטיסים מופיעים ב-`/door` ואפשר לסמן כניסה.

**עדכונים חיים:** כל כתיבה ל-`orders`/`tickets` שולחת מהטריגר `_notify_change` הודעת "changed" ריקה
מתוכן (בלי שמות או טלפונים) לערוץ ה-Broadcast הציבורי `event-updates`, ו-`/door` ו-`/admin` טוענים
מחדש דרך הפונקציות המוגנות. אם Realtime כבוי, המסכים מתעדכנים בכל מקרה כל 20 שניות.

## הערות

- **אבטחה:** למפתח ה-anon אין גישה ישירה ל-`orders`, `tickets` ו-`events_config`: לא קריאה (שמות
  וטלפונים לא נחשפים) ולא כתיבה (אי אפשר לסמן הזמנה כ"שולם" מבחוץ). כל פעולה עוברת דרך פונקציה
  ב-`schema.sql` שרצה כ-SECURITY DEFINER:

  | פונקציה | מי | מה |
  |---------|----|----|
  | `sold_count()` | כולם | מספר הכרטיסים שנמכרו (מספר בלבד) |
  | `create_order(...)` | כולם | הזמנה חדשה בסטטוס `pending`, רק בחלון המכירה |
  | `verify_pin(pin)` | כולם | מחזיר `admin` / `helper` / `null` |
  | `door_tickets(pin)`, `set_check_in(pin, ...)` | סדרן או מנהל | רשימת המשולמים וסימון כניסה |
  | `admin_orders(pin)`, `set_order_status(pin, ...)`, `admin_create_order(pin, ...)` | מנהל | ניהול ההזמנות |

  `tiers` נשאר קריא לכולם כי הוא רק מחירון.
- **קודים:** ה-PIN-ים יושבים רק בבסיס הנתונים. אחרי שקוד מתקבל, הדפדפן שומר אותו ב-`sessionStorage`
  (עד סגירת הלשונית) ושולח אותו עם כל קריאה, וכל פונקציה בודקת אותו מחדש. אם מחליפים קוד באמצע
  האירוע, מי שמחובר עם הקוד הישן מוחזר למסך הקוד. קוד מנהל פותח גם את `/door`.
- **מגבלות ידועות:** זו הגנת "קוד משותף", לא אימות משתמשים, ואין הגבלת ניסיונות על הקוד (לכן קוד
  ארוך). בנוסף, כל אחד יכול ליצור הזמנות `pending` שתופסות מקום עד שהמנהל מבטל אותן.
- **ביטול הזמנה** מחזיר את המקומות למכירה ואינו הפיך — `set_order_status` לא מחייה הזמנה שבוטלה,
  כי זה היה עוקף את בדיקת הקיבולת.
- **בחירה מאנשי קשר:** `navigator.contacts.select` נתמך בפועל רק ב-Chrome אנדרואיד על HTTPS.
  בכל סביבה אחרת הכפתור פשוט לא מוצג והמנהל מקליד ידנית.
- **CSV:** הייצוא נכתב עם UTF-8 BOM כדי שאקסל יציג עברית נכון.
- **עיצוב:** Neo-Brutalist / Pop-Art. Tailwind v4 מוגדר מ-CSS ולא מקובץ `tailwind.config.js`,
  ולכן כל הטוקנים (`brand-sky`, `brand-lime`, `brand-yellow`, `brand-coral`, `shadow-brutal*`,
  הגופן Rubik) יושבים בבלוק `@theme` שב-[`src/index.css`](src/index.css). העננים והשמש הם
  SVG inline ב-`src/components/ui.jsx` — אין קבצי תמונה ואין בקשות רשת לנכסים.
